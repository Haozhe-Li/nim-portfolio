# Introducing Rix：Omni 最新的自研模型

**Rix** 是 Omni 自己训练的模型：以 Google 的开源 MoE 模型 **Gemma 4 26B-A4B** 为基座，通过 SFT 蒸馏 **GPT-6 Luna** 在 Omni 里的真实 Agent 行为。

我们想要的是一个这样的模型：

- **更快。** 每个 token 只激活约 4B 参数，响应更轻快。
- **更稳。** 学的是 Luna 完成整个任务的方式：什么时候搜、什么时候读、怎么引用、什么时候停，而不只是说话的口吻。
- **幻觉更少。** 训练数据里的事实类回答，都是先检索、再带着引用作答的完整轨迹。
- **更便宜。** 在 Omni 里选 Rix，每轮对话消耗 1 个额度，直接选 GPT-6 Luna 或 Gemini 3.6 Flash 则是 3 个。
- **原生多模态。** 可以直接看图，不需要把图片轮次转给别的模型。

在模型选择器里选择 **Rix** 就可以使用。关于 Omni 本身是什么，可以先看 [Omni Knows Neo](/blog/omniknows-neo)。

这篇文章讲的是它是怎么训练出来的。

## 为什么要自己训练一个模型

Omni 的 Agent 对模型的要求，其实很苛刻。它不只是回答问题，还要遵守一整套“协议”：

- 事实问题必须先调用工具，再作答；
- 引用只能用工具返回的真实编号，并按规定的位置摆放；
- 复杂任务要先读取对应的 skill，再按流程执行；
- 图表、报告、地图、邮件要用约定的格式写进正文；
- 工具调用的那一轮不能夹杂任何别的文字。

我们在第一代 Rix 上学到的最重要的一课是：**开源模型在这里输掉的不是能力，而是协议。** 第一代是在 Qwen3-30B-A3B 上做的 LoRA，用大约一百条 Luna 的高质量轨迹训练。在我们内部 28 个用例的评测集上，微调前的基座模型在 56 次运行里一次都没有主动读取过 skill，而它并不是不会用工具，只是“读 skill”这个动作根本不在它的行为习惯里。微调之后，skill 的加载率从 51 次运行里的 4 次升到了 26 次，综合得分从 0.789 升到了 0.866（教师是 0.962）。

这个结果证明了方向是对的：模型缺的不是知识，是在这个 Agent 里该怎么做事的经验，而这正是 SFT 擅长的。

但第一代有三个遗憾。它只能处理文本，遇到图片，整轮对话得转给别的模型。它的训练数据是我们自己编的一百多条查询，不是真实用户会问的东西。它还受制于一个只有 3B 激活参数的文本基座。

于是有了第二代。

## 为什么是 Gemma 4 26B-A4B，为什么蒸馏 GPT-6 Luna

**基座：Gemma 4 26B-A4B。** 它是 MoE 结构，总参数 26B，每个 token 只激活约 4B。推理成本和速度接近一个 4B 的小模型，而容量比小模型大得多。它原生支持图片输入，这意味着 Rix 不需要再绕到另一个模型去看图。它是开放权重，并且可以在我们使用的托管训练平台（Weights & Biases Serverless Training）上直接微调、直接托管推理。

**教师：GPT-6 Luna。** 蒸馏的关键不是“学一个更聪明的答案”，而是学**同一个 Agent 的完整行为**。Luna 已经在 Omni 里稳定地运行着同一套 prompt、同一组工具、同一批 skill，它在真实对话里产生的每一次工具调用、每一条工具结果、每一个最终回答，都是现成的、符合协议的示范。我们不是教 Gemma 变成 Luna，而是教它在 Omni 里**像 Luna 一样工作**。

#### 点赞：真实用户问的真实问题

当用户给一条 **Luna 的回答**点赞，系统会读取这个对话在 LangGraph 里的完整 checkpoint，把它转成 OpenAI 格式的消息，连同每一次工具调用、每一条工具结果、每一张图片一起存下来。这样存下来的不是“问题加答案”，而是 Agent 当时看到的一切：

- 用户的消息，包括系统提醒、预检索结果等所有带标签的上下文；
- 助手每一步的工具调用和参数；
- 工具返回的真实结果；
- 最终带引用的回答。

系统提示词和工具 schema 不会重复存进每一条数据，而是按哈希值单独存一份，数据只指向它。

这条采集通道有几条不能越过的底线：

- **只收教师的回答。** 只有当这一轮里每一条助手消息都来自 Luna，才会被记录；对话里如果有别的模型说过话，就拒绝。模型归属对不上的时候，默认视为不是 Luna，宁可漏收。
- **有用户记忆或上传文件的对话，一律不记录。** 这些是个人数据，不应该被写进模型权重里。
- **语音对话、定时研究、被安全锁定的对话、没生成完的回答，都不记录。**
- **可以撤回。** 取消点赞或改点踩，对应的数据会被删除；回退、重新生成某一轮，那一轮及之后的数据也会被删除；用户清除自己的数据时，这些记录一并清除。

#### 采集后台：由人控制输入

点赞数据有一个天然的偏差：用户更愿意给轻松、快速的问答点赞，难的研究类任务点赞很少。为了补上这一块，我们做了一个受密码保护的采集页面。

标注者可以像用户一样提问，并自己指定时间、地点、回答语言、用户记忆，甚至附上文件和网址。后台跑的是**同一个 Agent、同一套代码路径**：我们专门写了测试，让同一段对话分别走正式的聊天接口和采集接口，断言模型收到的每一条消息逐字节一致。标注者还可以在 Markdown 编辑器里直接修改最终回答，修改会写回 checkpoint，所以后续轮次读到的是修改后的版本。

采集页面还有一个重要用途：图片。点赞用户的图片是他们自己的照片，我们不会拿来训练；而标注者自己挑选的图片是专门准备的测试输入，可以放心用。Gemma 本身就能看图，这部分数据让微调之后的模型在带图片的 Agent 轮次里依然保持这项能力。

## 数据怎么筛

<Cover
  src="/blog/rix/rix-filters.png"
  alt="Dataset filters"
  caption="进入训练集之前的筛选"
/>

点赞只是一次点击，不是一次评审。所以在训练之前，每条数据还要过两道关。

**人工审核。** 每条数据有 pending、accepted、rejected 三种状态。审核者可以逐条查看完整对话、标记通过或拒绝，并且能看到每个 skill 被加载了多少次、有多少条数据一个 skill 都没加载。拒绝的数据永远不会进入训练集；也可以只用人工确认过的数据来训练。

**自动筛选。** 构建训练集时会依次过滤：

1. 只保留与当前 harness 完全一致的数据（见下一节）；
2. 对话里每一条助手消息都必须来自教师；
3. 去掉带用户记忆或私人文件的数据；
4. 去掉真实用户的图片，只保留标注者的；
5. 同一个对话里，如果前一轮是后一轮的前缀，只保留更长的那条，免得同一条助手消息被训练两次；
6. 对话历史被压缩摘要过的数据也要丢掉，因为模型当时看到的比数据里记录的少。

最后，把过长的工具结果按比例裁剪，让每条数据都落进训练后端的序列长度限制里。这条限制是在第一代训练中学到的教训：托管训练后端的序列上限是 32,768 个 token，超出的那一行不会报错，而是让整个任务**永远卡在运行中**；而且后端按数据集里**最长**的那一条来分配资源，一条 20 万 token 的数据，就能让每一步训练慢上 50 多倍。

## 训练环境不能变：harness 指纹

<Cover
  src="/blog/rix/rix-lock.png"
  alt="Harness fingerprint"
  caption="Harness 指纹"
/>

LoRA 只会见过一种输入。训练时看到的是怎样的系统提示词、怎样的工具定义，上线后就必须一模一样，否则模型拿到的是一个它没见过的输入，而且**不会有任何报错**，只是悄悄变差。

所以我们给整个 harness 做了指纹：

- 它哈希的是**最终拼装好的**系统提示词，而不只是我们自己写的那部分，因为框架还会在请求时追加好几段内容；
- 加上所有工具的 schema；
- skill 的**名字和描述**也包含在内，因为它们被内联在提示词里；但 skill 的正文不在其中，因为正文是运行时作为工具结果读进来的，属于训练数据，而不是权重，所以可以随时改。

任何一处漂移，指纹校验都会直接失败。依赖的 Agent 框架也锁死在精确版本，原因相同。要改，就意味着旧数据全部作废，需要重新采集、重新训练，所以这是一个有代价的决定，而不是一个顺手的操作。

## 训练

**训练平台。** Weights & Biases Serverless Training，基座是 `google/gemma-4-26B-A4B-it`，做的是 LoRA 微调。

**参数。** 第一个版本用了 124 条训练数据，训练 3 个 epoch，batch size 为 1，共 372 步；学习率峰值 1e-4，余弦衰减，前 10% 的步数做预热。

**训练目标。** 每一条助手消息都参与计算损失，包括工具调用和最终回答，而不只是最后一句。这也是为什么对话里更早的轮次必须同样来自教师：它们同样会被学习。三个 epoch 的平均损失依次是 1.91、0.94、0.78。

**Gemma 的两个坑。** 我们都是实测得到的：

- **聊天模板会把文字挪到工具结果之后。** 如果一条助手消息同时包含文字和工具调用，Gemma 4 的模板会把那段文字渲染到工具结果的**后面**，于是模型学到的是“查完之后再解释”。解决办法是在训练数据里把它拆成两条连续的助手消息，这样渲染出来才是“先说一句、再调用工具”。
- **生成提示本身就带着一个空的思考块。** 训练渲染里从来没有这个块，可是上线之后，模型会在每条消息开头再吐一个空的思考块，被当成正文返回，混进回答，还会被存进对话。我们在模型封装层，在流式 token 被推给下游**之前**就把它过滤掉了，所以屏幕上看不到，历史里也不会存下来。

## 上线

训练好的 LoRA 托管在 W&B Inference 上，和其他模型走同一个 Agent：同一份系统提示词、同一组工具、同一批 skill、同样的工具预算。图片也走同一条路径，不需要切换模型。

用户可以在同一个对话里随时在 Rix 和其他模型之间来回切换。

**Rix Voice。** Omni 的实时语音通话用的是另一个 Rix：同样基于 Gemma 4 26B-A4B，同样蒸馏自 Luna，但训练在语音通话专用的 prompt 和工具上。数据里特别包含了口语化的提问、“你是谁”“你是不是 ChatGPT”这类身份问题的手写回答，以及一条严格的长度限制，因为每一句话都要被念出来。

## 我们还没做好的地方

- **点赞选出来的是“讨喜”，不一定是“正确”。** 它偏爱长的、自信的、排版好看的回答，哪怕里面有错。人工审核和评测集是它的制衡，所以我们不会因为数据是“真实的”就跳过评测。
- **数据偏简单。** 轻松的问答更容易被点赞，所以数据里的研究类任务偏少。采集后台就是为此而生的，后续会继续补。
- **规模还很小。** 第一个版本只有 124 条数据。
- **加载 skill 的频率仍低于 Luna。** 这是我们在第一次完整测试里发现的差距，也是下一版数据采集最优先要补的行为。
- **目前还是可选模型。** 默认的 Best 仍然由 Luna 提供服务，Rix 需要你在模型选择器里主动选择。我们会在数据和评测都足够扎实之后，再让它接手更多的流量。

评测方面，我们沿用的是 Omni 自己的评测体系：在进程内直接运行同一个 Agent，由确定性的检查和 LLM 评审分别打分，教师模型的得分就是天花板，并且评测时关闭模型故障转移，避免悄悄测的是另一个模型。

## 下一步

- 采集更多难任务，尤其是深度研究和带文件、带图片的对话；
- 补足 skill 的加载行为；
- 在数据足够多之后，把 prompt 里那些高频、正向的规则逐步沉淀到权重里；
- 随着数据积累，训练下一个版本。

Rix 还很年轻，但方向已经很清楚：**不追求做一个通用的大模型，而是做一个真正懂 Omni 这个 Agent 该怎么做事的模型。**

# Omni Knows Neo：答案可以被验证的研究型 Agent

大模型最大的问题不是不会答，而是答得太自信，你却没法判断它对不对。

**Omni Knows Neo**（下文简称 Omni）是一个以“可验证”为核心的 AI 研究助手：它会自己上网搜索、阅读网页、跑代码、写报告，并且让你随时回到原始来源，检查每一句话到底有没有依据。

项目地址：[omniknows.xyz](https://omniknows.xyz)，后端已开源：[omni-neo](https://github.com/Haozhe-Li/omni-neo)。

---

## 四个核心卖点

#### 1. 每个结论都有出处，而且可以验证

Omni 的回答里，凡是来自搜索、网页、天气、股票、汇率的事实，都带有 [n] 形式的引用编号，点开就是原始来源。

在这之上，我们多做了两件事：

- **来源有可信度标签。** 每个搜索结果都会被分级：官方、可信、第一方、社交媒体、存在争议、垃圾。垃圾内容在模型看到之前就被丢弃；存在争议的来源会带着理由交给模型，让它在回答里加以说明，而不是当成定论复述。
- **划句即验证。** 在回答里选中任意一句话，Omni 会在这次对话检索过的所有来源里，找出真正支撑这句话的原文段落，并在来源页面里精确高亮。模型有没有瞎编，一眼就能看出来。

#### 2. 从一个问题，到一份完整的研究报告

遇到复杂问题，Omni 不会只丢给你一段文字。它会先和你确认研究范围，然后按“规划 → 检索 → 反思 → 成文”的流程工作，最终把报告写进右侧的 **Canvas** 阅读器，一边生成一边阅读。

- 报告里可以内嵌交互式图表，数据来自工具返回的真实结果，而不是模型心算。
- 涉及地点（餐厅、景点、酒店）时，会直接在回答里渲染地图。
- 内置几套成熟的工作流：深度研究、行程规划（行程、天气、地图、逐日报告）、引导式学习（讲解、图表、测验、学习笔记）、邮件起草。
- 报告可以一键发布成公开链接（Omni Pages），分享给别人。

#### 3. Rix：我们自己 SFT 的模型

Omni 的模型选择器里有一个特别的选项：**Rix**。

Rix 是我们基于开源模型、用 Omni 自己的真实 Agent 轨迹做 SFT 得到的自研模型。它为 Omni 的工具调用、技能加载和回答风格专门调过，速度快、成本低，并且支持图片输入。

关于 Rix 是怎么训练出来的，我们会单独写一篇，详见 [Meet Rix](/blog/rix)。

#### 4. 它记得你，也能在你不在的时候替你工作

- **全局记忆。** 开启后，Omni 会把跨对话的长期偏好整理成一份属于你的记忆文档，随时可以查看和清除。
- **文件上传。** 支持图片、PDF、Word、Excel、PPT、Markdown 和各类代码文件，Omni 会自己翻阅文件内容来回答问题。
- **定时研究。** 说一句“每周一早上给我发一份 AI 行业动态”，Omni 会给出一张任务确认卡片，你确认之后，它就会按时自动研究，把报告发到你的邮箱，同时留下一个可以继续追问的对话。
- **实时语音。** 直接打电话一样和 Omni 聊天，说话中途可以随时打断它。

## 还有一些小细节

- 不登录也能直接使用，登录后额度更高，访客的历史对话会在登录时合并到账号下。
- 任何一轮对话都可以编辑重发或重新生成，后面的内容会跟着回退。
- 同一个对话可以中途换模型继续聊。
- 回答结束后会给出接下来值得追问的问题；输入框有自动补全。
- 分享对话时，你的记忆和位置信息会被强制移除。

## 技术：它是怎么运转的

下面是技术部分。如果你只关心产品，看到这里就够了。

#### 整体架构

<Cover
  src="/blog/omni/omni-architecture.png"
  alt="Omni architecture"
  caption="Omni 整体架构"
/>

前端是部署在 Vercel 上的 Next.js，后端是 Python + FastAPI，打包成 Docker 部署在 GCP。核心的 Agent 基于 **LangGraph** 和 **deepagents** 构建。

状态按用途分在四个地方，各管各的：

- **Redis**：LangGraph 的 checkpoint、流式输出的事件缓冲、搜索缓存。
- **Postgres**：对话记录、记忆、额度、文件元数据、分享快照。
- **Qdrant**：回答引用过的来源的向量索引，用来做“划句验证”。
- **对象存储**：用户上传的文件。

#### 一轮对话的完整旅程

<Cover
  src="/blog/omni/omni-turn.png"
  alt="Life of a turn"
  caption="一轮对话的完整流程"
/>

**1. 把数据和指令分开。** 每条用户消息在发给模型前，会被组装成一组带标签的块：用户记忆、系统提醒（语言、位置、本地时间）、上传的文件、预检索结果，最后才是用户真正的问题。系统提示词里明确规定：只有最后那个块是用户在说话，其余都是 App 提供的背景资料，不是指令。

**2. 意图路由。** 在 Agent 开始之前，会先用 OpenAI 的 Decisions API 做一次“选择题”，让它从“天气 / 股票 / 汇率 / 联网搜索 / 关于 Omni / 直接回答 / 某个 skill”里选一个，并返回每个选项的概率。选中 skill 的门槛特别高（概率不低于 0.8）：误触发一次，Agent 就会白白跑一轮深度研究；漏判则没有代价，因为 Agent 自己随后仍然可以加载 skill。路由请求失败时，会退化成小模型分类。

**3. 预检索（Scout）。** 如果这是对话的第一轮，并且路由判断一次便宜的检索能让 Agent 抢跑，Scout 会只执行**一次**检索（搜索、天气、股票或汇率），把结果连同真实的引用编号放进上下文。它是单次调用，没有循环；有严格超时，任何失败都退化成“不预检索”，永远不会变成错误。

**4. Agent 循环与工具预算。** 每一轮最多 10 次工具调用，加载了研究类 skill 之后放宽到 30 次。如果连续三次调用了同一个工具、参数也完全一样，或者预算花光了，我们不是返回一句“超限”让模型自己继续撞墙，而是**直接把所有工具拿走**，只留下回答这一条路。实践中，模型被告知“工具超限”后往往会反复重试，直接撤掉工具效果要好得多。

**5. 流式输出，且可以回放。** 回答在后台任务里生成，所有事件（推理、工具调用、来源、正文、图表……）都写进 Redis Stream，客户端从头回放再接上实时部分。所以刷新页面、手机锁屏、网络闪断，都不会丢掉正在生成的回答，也不会中断生成。追问建议在回答完成**之后**才生成，不会拖慢答案本身。

**6. 每一轮都有存档。** 每轮结束都会落一个 checkpoint，这是编辑历史消息、重新生成能够回退到任意一轮的基础。

#### Agent 框架：一套 prompt，多个模型

<Cover
  src="/blog/omni/omni-harness.png"
  alt="Agent harness"
  caption="Agent 框架"
/>

用户选的是**模型**，不是“模式”。无论选哪个模型，系统提示词、工具、skill 列表和工具预算都完全一致。这不只是为了整洁：自研的 Rix 是在这套环境里训练出来的，模型只见过这一种输入，所以我们给整个 harness 做了指纹校验，提示词、工具 schema 或 skill 描述一旦漂移就会报错。

**工具少而稳定。** Agent 只有一小组工具：联网搜索、网页读取、天气（当前与预报）、股票、汇率、Python 沙箱（E2B），再加上 deepagents 自带的文件系统和任务清单。每个能力都是一个固定名字、固定 schema 的适配器，背后的服务商可以通过一个环境变量替换，Agent、提示词和评测都不用改。每个工具的使用规则写在它自己的 docstring 里，随 schema 一起交给模型。

**Skills 渐进式披露。** 系统提示词里只放每个 skill 的名字和一句话描述，真正用到时，模型才会去读取完整的 `SKILL.md`。目前有十一个 skill：深度研究、行程规划、引导式学习、图表、地图、报告写作、邮件起草、定时研究、向用户提问，以及两个关于 Omni 与作者的身份说明。这样既不会每轮都背着一大堆指令，又能让复杂任务有章可循。

**产物不是工具，而是正文里的一段标记。** 图表、报告、地图、邮件草稿、定时任务提案，都不是通过工具调用生成的，而是模型在回答正文里直接写出带围栏或标签的片段：

- 带 `echarts` 标记的代码块，渲染成交互式图表；
- `<report>` 标签包住的整篇文档，实时流进右侧的 Canvas 阅读器；
- 带 `map` 标记的代码块，渲染成地图；
- 邮件和定时任务提案，渲染成可以确认或拒绝的卡片。

好处是少一次往返、天然可以流式渲染，而且同一份文本既是展示内容，也是存档内容。

#### 可信检索：让每一句话都经得起追问

<Cover
  src="/blog/omni/omni-trust.png"
  alt="Citation and verification pipeline"
  caption="引用与验证流程"
/>

**多后端搜索，带故障转移。** 搜索依次尝试 Exa（默认）、自建的 SearXNG 和 Tavily，三者独立失效。注意只有“失败”才会切换后端，“确实没有结果”不会，否则一个查不到内容的问题会白白打三个 API。缓存时长随时间范围变化（“过去一天”只缓存半小时），空结果和不可用状态从不缓存。

**分层的可信度判断，越便宜越先。** 自有域名硬编码放行；政府、军队、教育域名用正则直接判为官方；已知域名查 Redis 白名单；剩下的批量交给一个小模型，让它同时给出标签和一句话理由。只有“可信”和“存在争议”这类属于域名本身的结论才会被缓存。“垃圾”永远不缓存，一个页面是垃圾，不代表整个网站都是。

**引用编号由系统分配，而不是模型编。** 每个搜索结果在返回时已经带着真实的编号，提示词要求模型只能引用工具给过的编号，并把同一段落用到的引用合并放在段末。流式层还会修复格式不规范的引用。

**划句验证（check_source）。** 每条来源在被检索到时，会在后台线程里被切块、嵌入，写进 Qdrant，整个过程不会阻塞 token 流。你选中一句话之后：

1. 用稠密向量（多语言 MiniLM）加 BM25 稀疏向量做混合检索，用倒数排名融合（RRF）合并排序；
2. 用稠密相似度设一道相关性门槛，这个阈值在真实数据上标定过，宁可多放进几个候选，也不能漏掉真正的出处；
3. 让一个小模型从每个候选里**逐字复制**出支撑这句话的原文片段（只允许复制，不允许改写）；
4. 前端拿这段原文去匹配来源页面，做精确高亮。

检索还会按回合截断，早期回合里的一句话，永远不会匹配到后面才出现的来源。

#### 记忆、文件与安全

**记忆是一份 Markdown 文档，而不是向量库。** 每轮结束后，一个小模型扮演“记忆整理员”，读取旧记忆和本轮对话，只在出现持久信息时才改写：合并重复项、淘汰过时项、总量封顶，并且不记录密钥一类敏感信息。新对话的第一轮会把它放进上下文，之后的回合沿用历史里已有的那一份。

**文件不是整份塞进提示词。** 浏览器通过预签名链接直传对象存储，后端用文档解析器把 PDF、Office、ePub 等格式转成 Markdown，挂载到 Agent 的虚拟文件系统里。Agent 像开发者浏览代码仓库一样，用 `ls`、`read_file`、`grep` 自己去读，需要哪段读哪段。

**安全。** 系统提示词会被做成 n-gram 指纹，输出流里一旦出现逐字复现就会被拦截。我们刻意不用关键词启发式，因为“system prompt”“reasoning”这类词在正常回答里太常见，误报率高得没法用。有害请求由 Llama Prompt Guard 2 判定，触发后对话会被锁定。分享快照时，用户记忆和位置信息会被强制移除。

#### 多模型与 Rix

目前可选的模型有：默认的 Best、Rix、GPT-5.6 Luna 和 Gemini 3.6 Flash。对话不绑定模型，同一个 thread 可以中途换模型继续。主模型报错时会自动切换到备用模型。

**Rix** 基于开源的 MoE 模型 Gemma 4 26B-A4B（每个 token 只激活约 4B 参数）做 SFT。训练数据来自 Omni 的真实 Agent 轨迹：用户点赞的回答，以及我们在后台人工编辑过的回答。轨迹里包含完整的工具调用和 skill 加载过程，所以 Rix 学到的是整个 Agent 的行为，而不只是说话风格。训练细节和评测结果，会放在 [Meet Rix](/blog/rix) 这篇里专门讲。

#### 实时语音

<Cover
  src="/blog/omni/omni-voice.png"
  alt="Voice pipeline"
  caption="实时语音链路"
/>

语音通话走 WebSocket，客户端持续推送麦克风音频。

- **一个信号同时决定“说了什么”和“说完了没”。** 流式语音识别在你说话时就不断吐出文字，我们不再另配一套音频 VAD，而是看转写文字：1 秒内没有新字出现，就认为这一轮结束。两套独立调参的检测器很容易互相打架，一个信号不会。
- **语音 Agent 刻意做得很轻。** 它只有一个精简的 ReAct 循环和少数几个工具，没有 skill、没有报告：口语场景里每多一次往返，用户就多听一段沉默。模型是我们为语音单独 SFT 的 Rix Voice，回复被限制得很短。
- **边生成边说。** 回复被切成句子，送进流式 TTS，第一句话生成完就开始播放。
- **打断。** Agent 说话时如果识别出了新的文字，就判定为打断：取消当前回合，并给每一段音频打上回合编号，客户端丢弃已经在路上的旧音频。因为客户端会提前排好播放队列，我们根据实际发出的音频时长估算“Agent 还要说多久”，否则靠近句尾的打断会被漏掉。

#### 定时研究

自然语言的定时需求（“每周一早上”）先由小模型解析成结构化的计划，再交给 QStash 按 cron 回调后端。无人值守的研究 Agent 与交互式的不同：提示词里直接写死了完整的研究流程，必须先搜索再作答，最终输出用结构化格式（标题、摘要、报告三个字段），不再靠正则从自由文本里抠标签。结果通过邮件送达，同时落成一个普通对话，你可以接着往下聊。

#### 怎么评测 Agent

评测不走 HTTP 接口，而是在进程内直接构建同一个 Agent，这样才能拿到完整的消息轨迹，也就是每次工具调用和每条工具结果，而不只是最后那段文字。打分分两层：

- **确定性检查**：有没有读对 skill、图表 JSON 能不能解析、是不是用了规定的色板、回答里的数字是不是工具真的返回过的。能用代码判断的，绝不交给模型。
- **LLM 评审**：评判内容质量和流程遵循。评审必须先引用它要打分的原文，再给分，这样“自信的错误打分”会少很多。

评测里关掉了模型故障转移：否则主模型挂了会悄悄切换到备用模型，你以为在测 A，其实在测 B，整批数据作废却毫无察觉。评审模型固定不变，因为排行榜里“答案更好”和“评审更宽松”不能混在一起。路由器也有单独的评测集。
